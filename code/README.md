# Buy or Wait agent

Python 3.12. The existing deterministic baseline is extended with evidence
providers, immutable amendments, spending-change search and a seven-stage agent.
No solved output fields are passed to the engine.

## Setup and commands

```sh
python3.12 -m venv .venv
source .venv/bin/activate
python3.12 -m pip install -r code/requirements.txt
python3.12 -m unittest discover -s code/tests -v
python3.12 code/main.py evaluate-samples
python3.12 code/main.py trace --sample request_16
python3.12 code/main.py trace --request request_26
python3.12 code/main.py extract-evidence --samples
python3.12 code/main.py extract-evidence --samples --live
python3.12 code/main.py extract-evidence --all --live
python3.12 code/main.py predict --output output.csv
python3.12 code/main.py predict --offline --output output.csv
python3.12 code/main.py validate-output output.csv
```

Use the activated environment, or replace `python3.12` with `.venv/bin/python3.12`.
On systems without ensurepip, install the OS Python 3.12 venv package before setup.
All relative data/output paths resolve from the repository root, independently of
shell working directory. Absolute output paths are also accepted. `dataset/` is
read-only, enforced by the prediction writer. Output is written atomically after
all requested rows are produced. It is not generated by tests or sample evaluation.

**Offline is the default.** Only `extract-evidence --live` can instantiate the live
provider through the CLI. `predict`, `trace` and `evaluate-samples` always use the
cache. Extraction without `--live` reads cache only. Repeating a live extraction
command reuses matching cache entries and calls the model only on cache misses.
No live extraction or root prediction CSV was run during this implementation.

## Architecture

1. Input Request: typed `Request` containing exactly the eight input fields.
2. Retrieve Context: `Dataset.context`, user profile/events, scoped messages/images,
   request options and directional exchange rates. Blank request IDs retain user
   evidence; foreign-user links are rejected; future messages are excluded.
3. Reconstruct Financial Reality: evidence resolution yields copies of events;
   lifecycle and cash-state rules never mutate raw rows.
4. Build 90-Day Baseline: expand supported recurrence, simulate each date and
   calculate baseline safe-today capacity and earliest full-payment date.
5. Generate Payment Candidates: full, partial, supplied installments, waiting,
   and eligible spending-change variants.
6. Verify and Rank: explicit per-candidate checks; rank only valid plans in the
   challenge order. Spending-change cardinality is minimized during search, not
   added as an unauthorized ranking criterion.
7. Produce output.csv: deterministic explanation and exact column order; the
   `predict` command is the only CSV writer.

`BuyOrWaitAgent.evaluate(request)` in `agent.py` exposes all named stage methods
and returns `AgentEvaluation(row, result, trace)`. `planner.predict` is retained as
a compatibility wrapper using a fake provider. `main.py` remains the terminal entry.

## Evidence, cache and cost

`EvidenceProvider` has fake, cached and OpenAI implementations. OpenAI uses the
Responses API Pydantic Structured Outputs parser, as described in the
[official Structured Outputs guide](https://developers.openai.com/api/docs/guides/structured-outputs).
Its client is created lazily, retries are disabled, and output parsing/refusals are
handled without copying SDK error bodies or headers into diagnostics.

`config.py` uses `REPO_ROOT = Path(__file__).resolve().parents[1]` and
`load_dotenv(REPO_ROOT / ".env")`. Environment variables:

* `OPENAI_API_KEY`: used only when a live client is created; never printed.
* `OPENAI_EVIDENCE_MODEL`: extraction model; falls back to `OPENAI_MODEL`, then
  `gpt-4.1-mini`. Keep the model stable between extraction and offline prediction.
* `EVIDENCE_INPUT_COST_PER_MILLION`, `EVIDENCE_OUTPUT_COST_PER_MILLION`: optional
  Decimal rates. No prices are invented. Cost is unknown when rates or token usage
  are unavailable; offline operations have zero new model cost.

Cache lives in ignored `code/evaluation/evidence_cache/`. Keys include SHA-256
source content, model, prompt version, source metadata and relevant event context.
Only structured facts and usage metadata are persisted, never source image Base64,
authorization headers or API keys. Changing any keyed input invalidates the entry.
The model sees financial event context, not payment options, solved labels or an
instruction to calculate affordability. Facts cannot contain decisions or schedules.
All evidence is untrusted and source/event identities are checked again after
extraction. Confidence below 0.8, unknown links, incomplete facts and failed
extractions remain auditable unresolved issues, never zero amounts.

Image fields follow the requested schema. Message fields add nullable description,
category/direction/type for new-event creation, scope for single versus continuing
amendments, and a literal percentage-change field. A percentage is applied using
Decimal in reconstruction, never calculated by the model. An incomplete new event
is not guessed. A single new fact is not repeated without supported recurrence.

Conflict precedence is explicit cancellation/settlement/amendment, then newer
records from the same source, then settled facts, then conservative amounts/dates.
Message source identity uses the supplied `source_type` within one user; the CSV
has no separate issuer ID. Conflicting extracted currencies block certification.
A next-payment confirmation preserves the historical event and creates a distinct
future occurrence. Continuing amendments take effect before recurrence expansion.

## Financial assumptions and remaining limits

* The starting snapshot includes settled transactions on or before request day.
  Historical cash is never replayed. Pending debits are assumed not already held
  in that balance and are reserved immediately, once. Pending credits, failed and
  cancelled rows, unrealized values and non-cash events contribute no cash.
* Lifecycle links can represent replacements, refunds, retries or investment cash
  legs. Settled replacements/cancellations suppress prior authorizations. Refunds
  and investment sales are distinct opposite-direction cash flows; a possible
  duplicate debit remains reserved until resolving evidence says otherwise.
* Use only the exact dated directional FX row. No inversion, interpolation,
  live rate or carry-forward is allowed. Missing required rates block certification
  with an auditable error. Decimal precision is retained; safe capacity is rounded
  down to cents and verified by simulation.
* Forecast includes request day through day +90 (91 dated ledger entries). The
  specification says “next 90 days” without an explicit endpoint convention; the
  inclusive interpretation is documented and tested. Same-day essential debits
  precede credits conservatively; request payments follow those known flows. Every
  intermediate balance, including the opening balance, must preserve the reserve.
* Monthly recurrence requires three consecutive monthly observations with a
  consistent calendar day. Groceries, transport and dining are grouped across
  merchants; regular day intervals also require three observations. Irregular or
  stale patterns are flagged rather than silently declared reliable. Variable
  recurring debits use the maximum of the last three known amounts. Payroll uses
  the latest regular amount; bonuses/commissions/seasonal/freelance receipts are
  not automatically projected. Explicit future confirmed salary counts once.
* This conservative recurrence heuristic remains inaccurate on the public samples.
  No sample labels are used to select rules, override amounts or tune constants.
  Missing historical image amounts remain relevant to recurrence; unknown active
  debits block certification. The fixed output enum has no unknown state, so an
  uncertified zero/not-recommended fallback is accompanied by an explicit explanation.
* Capacity and earliest full-payment date are calculated before spending changes,
  independently of payment preferences. Earliest uses the remaining original
  forecast, not a newly rolling 90-day horizon. Baseline breaches cannot be fixed
  merely by choosing a later payment date.
* Installments preserve supplied start dates and literal 28/30/31-day intervals.
  All 790 supplied options satisfy exact sum=total=principal+fee. Validation now
  enforces exact equality, correcting the Phase 1 rounding-tolerance assumption.
  The installment limit constrains both payment count and elapsed calendar months
  measured from first payment; this interpretation remains documented uncertainty.
* Spending changes affect inferred future recurring expense flows only, not
  already-authorized pending debits or historical transactions. Profiles must allow
  the action; protected/fixed expenses cannot change; reduction floors are enforced.
  Search tries one, two then three changes, prunes by optimistic savings bounds,
  tightens reductions to the smallest sufficient cent amount and records each
  change's necessity. New one-off bills are not treated as adjustable recurring flows.

## Tests, evaluation and auditing

Tests use fake facts or a mocked Responses client and make no network calls.
They cover all four affordability outcomes, cash states, conflict precedence,
image amounts, FX, recurrence, capacity maximality, calendar boundaries, schedules,
preferences, spending changes, cache isolation, SDK schema generation and redaction.
The prediction writer is tested only with synthetic requests in a temporary folder.

Sample evaluation completes all predictions before loading expected output fields.
It prints exact-text and normalized Decimal/schedule accuracy for every field,
plus request accuracy with/without explanation. Text equality is not a semantic
explanation score. Reports are `evaluation/sample_results.{md,json}`; traces are
`evaluation/traces/<request_id>.{md,json}`. Each trace includes context counts,
evidence used/skipped, resolved events, projected flows with provenance, daily
balances, capacity verification, earliest-date attempts, every candidate/check,
invalid reasons, valid ranking keys and the final recommendation.

Usage reports distinguish extraction-only runs from full-dataset predictions.
Cached resolutions consume no new model tokens; historical extraction usage remains
in cache metadata. Final-submission usage must describe the actual final run,
which has not been executed. See `evaluation/agent_findings.md` for this run's
measured accuracy and remaining forecast mismatches. `phase1_findings.md` is the
historical pre-orchestrator report and is not the current score.
